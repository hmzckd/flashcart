# Place each order once per idempotency key with an insert-first key table

A client that sends `POST /api/orders` and loses the response cannot tell whether the order was placed. If it sends the request again, a second order is placed and the stock goes down twice. A client may now send an `Idempotency-Key` header with a string of 1 to 255 characters that it picks once per order. We store each key in `order_idempotency_keys`, where the key is the primary key, and the first statement of the transaction that places the order is `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`, the same insert-first pattern as ADR 0004. If the insert adds a row, the order is placed and its id is written next to the key in the same transaction. If it adds no row, the key has been used before: the request gets 201 with that order in its current status and the header `Idempotent-Replayed: true`, and nothing changes. If that order's product or quantity differ from the request, the request gets 422 instead. The header is optional, and a request without it works as before.

Two requests with the same key can run at the same moment, for example when the client gives up waiting and sends again while the first is still running. PostgreSQL makes the second insert wait until the first transaction ends. If the first commits, the second finds the key and answers with that order. If the first rolls back, for example with a 409 for insufficient stock, the second inserts the key and places the order itself. With 10 concurrent requests with one key, all 10 get 201 with the same order and the stock goes down once, with both stock-locking modes. With optimistic locking, the first request can also lose a version conflict to another buyer of the same product: its transaction rolls back, key included, the retry or a waiting repeat claims the key again, and the tests still see exactly one order for the key.

## Considered options

- **Check, then insert (`SELECT EXISTS`, then `INSERT`).** Concurrent requests all pass the check before the first one commits. The later ones then fail on the primary key with a duplicate key error, so the client gets a 500 instead of its order. The concurrency test failed this way in 3 of 3 runs.
- **Insert the key in its own transaction (`REQUIRES_NEW`).** The key is committed before the order exists. If placing the order then fails, the key stays behind without an order, and every retry with that key fails with a 500. Concurrent requests also find the key before it has an order. Each request holds two database connections at once, and in one of two runs the concurrent requests used up the pool of 10 and waited 30 seconds for a connection.
- **A unique key column on `orders`.** The order row is inserted only after the product is locked and the stock is decreased, so the key cannot go in first. A duplicate request would find out at the very end, after it had waited for the product lock, and the whole transaction would have to be rolled back and the existing order read in a new one.
- **Store the first response and send it back byte for byte.** It needs more storage and code to rebuild the response. A client that repeats a request wants to know about its order, and the order's current status answers that.
- **Make the header required.** Every existing client would get a 400 until it is changed.

## Consequences

- Keys are not tied to a customer, because FlashCart has no customer accounts yet. Two clients that pick the same key would get each other's order or a 422, so clients should use random keys such as UUIDs. Once there are accounts, a key should belong to one customer.
- `order_idempotency_keys` gets a row for every order placed with a key and is never cleaned up yet. Keys older than a day could be deleted, or kept in Redis with an expiry time, once the table grows.
- Only placed orders are remembered. A request that failed with 400, 404 or 409 changed nothing, so repeating it simply runs it again.
- A request that waits for another request with the same key holds a database connection while it waits, with no time limit. Many repeats of one slow request could take every connection in the pool (10 by default) and make other requests wait too. A `lock_timeout` on the insert would cap the wait if that ever shows up.
- `ON CONFLICT` is PostgreSQL syntax, so another database would need this one statement rewritten.
