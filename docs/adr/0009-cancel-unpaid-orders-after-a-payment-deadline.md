# Cancel unpaid orders after a payment deadline with a scheduled job

A pending order takes its units out of the stock as soon as it is placed. If the customer never pays, those units are lost to every other buyer, and in a flash sale that can be the whole stock. Every pending order now has a payment deadline of 15 minutes from the moment it was placed (`flashcart.payment.deadline`). A job inside the app, `UnpaidOrderCanceller`, runs 30 seconds after its previous run ended, behind the same `flashcart.scheduling.enabled` switch as the outbox relay. It reads the ids of the 100 oldest pending orders that were placed at least 15 minutes ago and cancels each one in its own transaction with `OrderService.cancelIfPaymentDeadlinePassed`. That transaction reads the order again and cancels it only if it is still pending and still past the deadline. The order becomes `CANCELLED` as if the customer had cancelled it: its units go back to the stock and an `OrderCancelled` event is recorded. No refund is requested, because nothing was paid. The order's `createdAt` now comes from the `Clock` bean instead of `Instant.now()`, so the tests can move the clock past the deadline.

A payment can arrive while the job is cancelling the same order. If the payment commits first, the job's transaction reads a paid order and leaves it alone. If the job commits first, the payment finds a cancelled order and a refund is requested, as for any payment the order cannot accept (ADR 0004). If both commit at the same moment, the order's version stops the second one (ADR 0003). A job that loses is retried, reads the paid order and leaves it alone. A payment that loses gets a 409, the provider sends the event again, and that delivery requests a refund. In a test where 10 due orders were paid while the job ran, each order ended either paid with no refund or cancelled with one `ORDER_NOT_PENDING` refund, in both stock locking modes. Across 24 runs, between 3 and 10 of the 10 orders were paid. Two jobs running at once, for example in two app instances, cancel each order once.

## Considered options

- **A new `EXPIRED` status.** It would tell an expired order apart from one the customer cancelled, but it needs a migration of the status check, new status changes and a new event type that the notification service would have to learn. For the customer and for the stock the result is the same as a cancel.
- **Cancel every due order in one transaction.** One failing order would roll back all of them, and the product row would stay locked for the whole batch while buyers wait.
- **Trust the query and skip the second check.** An order that is paid between the query and the cancel would be cancelled anyway, and because it is paid, a refund for the whole order is requested. With the check removed, the race test failed in 5 of 5 runs: a paid order was cancelled and its money sent back. A test that pays an order after the job has read its id failed every time, and a second job failed on every order the first one had already cancelled, with 10 errors in the log per run.
- **Check the deadline only when someone reads the order.** The units stay out of the stock until somebody looks at the order, so the stock stays wrong.
- **Let the database or a broker do it (`pg_cron`, a delayed Kafka message, a Redis key that expires).** Each needs more infrastructure, and the cancel still has to return the stock and record the event, which the app already does.
- **No index, or a full index on `created_at`.** On 500,000 orders with 5,000 of them pending, the query without an index read the whole table (parallel sequential scan, 32.5 ms, 5,394 buffers). With the partial index on pending orders it read 100 index entries (index scan, 0.17 ms, 102 buffers). The partial index took 128 kB, a full index on `created_at` 11 MB.

## Consequences

- An unpaid order is cancelled between 15 minutes and about 15 and a half minutes after it was placed. When more than 100 orders are due at once, the rest wait for the next runs: about 100 cancels every 30 seconds. After a large flash sale with thousands of unpaid orders this takes a while, and a larger batch or running again right away when a run was full would help.
- A payment that arrives after the deadline is refunded, even if the customer paid in good faith. The customer has to place the order again.
- When this version is deployed, every order that is already pending and older than 15 minutes is cancelled on the first run.
- In the job's query, `status = 'PENDING'` is written as a literal so that PostgreSQL can use the partial index. It still uses it when the cutoff is a bind parameter, which was checked with a generic plan.
- Several app instances each run the job and may pick the same orders. The version check keeps each order cancelled once, but the extra work is wasted. `FOR UPDATE SKIP LOCKED`, as in the outbox relay, would split the orders between them if that ever matters.
- An order whose cancel fails, for example because its retries run out, is logged as an error and tried again on the next run.
- `V9` builds the index with a plain `CREATE INDEX`, which makes new orders wait until the index is built. On a large `orders` table, `CREATE INDEX CONCURRENTLY` would avoid that, but Flyway would have to run that migration outside a transaction.
